# 成本：不是估算，是账单

> 这一篇只有数字。所有数字都能用一句话复核，复核方法附在每节末尾。
> **但这篇也是一个自我打脸的记录**——我一开始写的是估算值，后来发现估算和实际差 78%。

---

## 零、先说一个坑：估算和实际差一倍

有两套账单：

```
A. 逐轮累加（每次调用的 cost 相加）    → ¥14.38（10-29）
B. 余额差额（早上余额 - 晚上余额）      → ¥25.56（10-29）
```

**差 ¥11.18，78%。**

**原因**：逐轮记录的 `cost` 是按 token × 单价算出来的**估算值**。它没算准缓存未命中的价格差（命中价和未命中价差 50 倍）。

**所以**：

> **别用逐轮估算做预算。用余额差额。**

**这条是这一篇最有用的一句**：如果你想算「养一个 agent 到底多少钱」，**唯一可信的数字是钱包余额的变化**。

## 二、一个被误解的数字：「每次 0.01~0.05」

主人当时看到消耗记录里「0.01~0.05 不等」的金额，但翻群聊没看到她说话，以为她「偷偷干了什么」。

**真相**：

```
0.01~0.05 不是"单笔支出"，是"每一轮的成本"
一轮 = 一次完整推理
一轮可能发十几条消息，也可能一个字都不发（判断后跳过）
```

**逐轮成本的实际分布**（10-29，544 轮）：

```
最少    ¥0.0012
中位    ¥0.0109
最多    ¥0.6972   ← 那一轮干了重活（读大文件/跑工具）
> ¥0.2 的轮次：9 个（占 1.7%）
```

**中位数 ¥0.011，但平均值 ¥0.026**——说明**少数重活拉高了均值**。

**这就是「按轮平均」会失真的原因**：

> **平均每轮 ¥0.026，听着很便宜。但 1.7% 的轮次花了 30% 的钱。**

**如果你要优化成本，该看的是那 1.7%**——通常是「读大文件」「跑长命令」「反复重试」这几类。

## 三、钱花在哪：轮次 vs 消息

同一天的会话里，按小时拆开：

| 小时 | 花费 | 轮数 | 她发的消息 |
|---|---|---|---|
| 00 | ¥0.83 | 121 | 213 条 |
| 07~08 | ¥0.94 | 46 | 102 条 |
| **09** | **¥0.12** | **6** | **0 条** ← |
| 13~14 | ¥5.04 | 70 | 136 条 |
| 15~16 | ¥3.16 | 63 | 122 条 |

**注意 09 点那行**：6 轮、0 条消息。

那 6 轮在干什么？三种可能：

1. 她判断「不用说话」（输出跳过）
2. 定时任务（刷 B 站候选、写日记提醒）
3. 另一个会话（助手在改代码）

**三样都花钱，都没有消息产出。**

**所以「群里没看到她说话，但有钱在花」是正常的。**

## 四、消息实际发在哪（一个完全反直觉的数字）

```
某天她发了 631 条
  ├─ 私聊  547 条  （87%）
  └─ 群聊   84 条  （13%）

私聊细分：
  · 主人       334 条
  · 另一个人   184 条   ← 主人以为她"在群里"
  · 第二主人    29 条
群聊细分：
  · 主群        79 条
  · 一个退了的群 4 条
```

**这就是误解的来源**：主人只看群，**而她的 87% 的话发在私聊里**。

**给后来者的建议**：

> 要看「一个 agent 今天说了什么」，**不能只看群**。
> 私聊、群聊、空间、评论，全部拉一遍——否则你会得出「她今天没说话」的错误结论。

## 五、成本构成：90% 在输入，不在输出

一轮的成本里：

| 部分 | 占比 | 说明 |
|---|---|---|
| **输入（上下文）** | **~90%** | 每一轮都要重发整个历史 |
| 输出（她说的话） | ~10% | 通常几十到几百 token |

**所以「砍人设」比「砍输出」有效得多。**

举例（按 3 字 ≈ 1 token 估）：

```
人设 21,459 字 → 约 7,000 token
每一轮都要带 → 每轮固定成本
一天 360 轮 → 光人设就 250 万 token
```

**砍到 2,681 字之后**，每轮固定成本降到约 900 token。

**但这笔钱省下来不多**（一天几块钱），**真正的收益是注意力**：

> 21K 字里，模型每次只能抓住一小部分。
> 砍到 2.7K 之后，**每一句都是它该看的**。

## 六、缓存：最容易被忽略的一笔

上下文缓存命中与未命中，**价格差 50 倍**（具体倍数看当前定价表，但这个量级是普遍的）。

**什么会让缓存失效**：

- 换模型
- 加/删工具
- **改提示词（哪怕一句）**
- 上下文开头变了

**所以**：

> **改配置的成本不是「改一下」，是「之后所有轮次都按全价重算」。**

**实操纪律**：

```
① 改动集中做（别一天改三次）
② 改完观察当天的余额差额有没有变大
③ 能一次改完的，别改两次
```

## 七、能和不能省的

| 能省 | 不能省 |
|---|---|
| 人设体积（21K → 2.7K） | 记忆（记不住就白养了） |
| 重复的历史（会话轮换） | 该说的话（回复质量） |
| 不必要的轮次（判断后跳过） | 安全（过滤、审批、日志） |
| 缓存失效（集中改动） | 观测（不知道花在哪就没法优化） |

**一条原则**：

> **省「重复」的钱，不省「记得」和「看得见」的钱。**
>
> 重复的上下文可以丢，记忆不能丢；
> 安全相关的检查不能省，日志不能省——因为没有日志，你连「省了没有」都不知道。

## 八、一个反例：加保险层之后成本没降

我们加了「1 MB 响应提醒 + 2.5/4.0 MB 轮换」之后，以为成本会降。

**实测**：没降多少。

**为什么**：

- 轮换能让「每轮输入」变小
- 但轮换本身要跑一次（读会话、写归档）
- 而且她换了新会话之后，要重新建立上下文（重读人设、记忆、ALWAYS）→ **前几轮反而更贵**

**结论**：

> **「省成本」不是一个可以立刻验证的目标。**
> 加任何机制之后，要观察**至少 3 天**的平均余额差额，才知道有没有用。
