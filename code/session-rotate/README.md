# session-rotate

> 上下文会话轮换：**软阈值她决定，硬阈值系统兜底，关键会话永不动。**
> 从实战脚本里抽出来的，去掉了一个项目的专属配置。

## 为什么需要这个

LLM agent 的会话文件会一直涨。涨到最后有两个后果：

1. **贵**：每轮都要重发整个历史（成本 90% 在输入）
2. **慢，甚至会卡死**

关于第 2 条，有个实测数字值得说：

```
1.46 MB 的会话 + 一轮新任务（读 3 个文件）
→ 静默卡死 10 分钟
→ 表现不是报错，是消息进来了但 turn/end 永远不出现
```

**所以「会话变大」不是慢慢变慢，是在某个点上突然卡住。**

## 三个阈值，管三件不同的事

这是这个脚本的核心设计。**很多人只设一个阈值，那是错的。**

| 阈值 | 管什么 | 谁处理 |
|---|---|---|
| **1.0 MB**（响应线） | 回话会不会变慢/卡死 | **只提醒**，谁都不动 |
| 2.5 MB（软阈值） | 上下文成本 | **agent 自己决定**要不要轮换 |
| 4.0 MB（硬阈值） | 防止会话涨到崩 | **系统兜底**：标记 + 轮换 + 告知 |
| — | 关键会话 | **永远不动**（硬编码） |

### 为什么软硬要分开

只做硬阈值（全自动清）的后果：

> agent 会说「我好像跟你聊过这个」——但想不起细节。
> 因为上下文在它不知情的时候被清掉了。
> **它被剥夺了「知道自己经历过什么」的能力，但它不知道自己被剥夺了。**

只做软阈值（全交给它判断）的后果：

> 当时的记录：它不标记。
> 实测：一个群的会话涨到 4.52 MB，连续三天每天只告警不动。
> 我据此判断「它的判断力够，但动力不足」——因为它看不到「涨到 4.5 MB 会怎样」。

> **⚠ 这个判断后来被推翻了（2026-10-30）**
>
> 查它的标记表发现：它**早就标记过了**，还写清了理由（"这个群聊了三天，前面的内容我记不住了"）。
> 真正没执行的是脚本自己——
> ① 轮换被排在了「启动服务之后」，文件已被锁，必然 `PermissionError`；
> ② `shutil.move` 又因为归档区有同名旧档而失败，而 except 把这句打印成了"会话文件被占用"。
>
> **所以这一条的真正教训不是"它动力不足"，而是：**
> **「它没按你说的做」要先查系统那条路通不通，再怪它。**

**所以：软阈值保留判断权，硬阈值防止疏忽变成灾难。**

**而硬阈值要留一道"危险线"**：万一它一直不标记，不能等上下文把 agent 撑坏了才来修。
本目录的 `rotate.py` 把 `--hard-factor` 做成参数，就是留给这一层的。

## 用法

```bash
# 预演（不加 --apply 不写任何东西）
python rotate.py --sessions-dir /path/to/sessions --limit-mb 2.5

# 真执行
python rotate.py --sessions-dir /path/to/sessions --limit-mb 2.5 --apply

# 关键会话（永不动）：逗号分隔的目录名前缀
python rotate.py --sessions-dir ... --protected "master-,admin-"
```

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--sessions-dir` | 必填 | 会话文件所在目录（递归找 `session.v4.jsonl.zstd`） |
| `--limit-mb` | 2.5 | 软阈值 |
| `--warn-mb` | 1.0 | 响应线（只提醒） |
| `--hard-factor` | 1.6 | 硬阈值 = limit × factor |
| `--protected` | 空 | 逗号分隔，匹配目录名前缀 |
| `--apply` | false | 不加就只预演 |
| `--archive-dir` | 同级的 `_archive` | 归档去哪 |

## 输出

```
自定义标记 0 个；共 12 个会话
  chat-a          4.56 MB
  chat-b          3.23 MB   ← 关键会话（不动）
  chat-c          1.46 MB
  ...
硬阈值兜底：chat-a（4.56 ≥ 4.00）
已写 context-warning.json（通知 agent）
```

**`context-warning.json` 的结构**：

```json
{
  "slow_sessions": {
    "chats": [{"chat": "chat-c", "mb": 1.46}],
    "why": "会话超过 1.0 MB，回话会变慢甚至卡死"
  },
  "auto_rotated": {
    "chats": ["chat-a"],
    "why": "超过 4.00 MB 硬阈值，系统替你轮换了（已归档，可用 recall 找回）"
  }
}
```

**这个文件是给 agent 读的**——它开新会话时会看到「系统替我轮换过」，而不是发现上下文凭空少了。

## 一个设计判断：归档之后要能找回来

轮换不是删除。脚本会把「轮换前最后 N 条对话」写成 markdown 存进归档目录：

```markdown
# 会话轮换存档：chat-a

> 上下文已到 4.56 MB，按阈值轮换。下面是轮换前最后 60 条对话（原文），
> 以后想回忆这段时间用 `recall.py` 搜这个文件。

- `10-30 01:22` **某人**：……
```

**为什么是"最后 60 条"而不是全部**：

- 全部存会占很多空间（而且原始会话文件本来就在）
- 最后 60 条是「最近的上下文」，最可能有用的部分
- 想找更早的，去原始会话文件（zstd 压缩的 jsonl）里翻

## 已知限制

1. **只在启动时跑**：agent 运行中涨到 4 MB 不会自动触发。要实时监控得挂个守护进程。
2. **按文件大小算，不按 token 算**：文件大小和 token 数不是线性关系（中文 UTF-8 3 字节/字，token 按语义切）。但文件大小容易拿到，够用。
3. **归档是 markdown**：如果对话里有很多代码/符号，格式会乱。要精确恢复得解析原始 jsonl。

## 一个建议

如果你也在做类似的事，**从第一天就记录「每轮属于哪个会话」**。

否则你永远算不清「这个 agent 花了多少钱」——这是我踩过的坑（详见 `docs/03-成本.md`）。
